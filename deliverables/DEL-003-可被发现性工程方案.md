# AGI Engine 可被发现性工程方案

> 适用范围：单文件 HTML PWA + GitHub Pages（`https://fnhiq23.github.io/agi-engine-v3/`），无服务端渲染、无构建步骤。
> 核心原则：**只描述真实存在的能力**。不提区块链/代币/智能合约，不承诺收入，不刷量。所有建议在"改一个 `index.html` + 往仓库根目录丢几个静态文件"的约束内可执行。

## 现状诊断（先看问题，再开药方）

| 项 | 当前状态 | 后果 |
|---|---|---|
| `<title>` | `AGI Engine — Your Personal AGI` | 没有可搜索的产品类别词，用户搜 "private AI assistant" 不会出现 |
| `<meta description>` | 缺失 | 搜索结果摘要由引擎随机抓取正文，转化率低 |
| Open Graph / Twitter Card | 缺失 | 分享到 X / WhatsApp / 微信外链时无标题无图，点击率低 |
| JSON-LD 结构化数据 | 缺失 | 拿不到富媒体摘要，AI 也无法结构化理解产品 |
| `<html lang>` | 静态 `zh-CN` | 英文为主要搜索战场却声明为中文，语言信号错位 |
| 关键营销文案 | 部分由 JS 渲染 | 搜索引擎与 AI 爬虫多不执行 JS，看不到产品价值 |
| `robots.txt` / `sitemap.xml` / `llms.txt` | 缺失 | 无抓取引导，AI 搜索无权威事实源 |

**一句话结论**：产品不是不好，是"对机器不可读"。下面五节按"先让机器读懂 → 再让人找到 → 再让 AI 引用 → 最后放大分发"的顺序展开。

## 3. 多语言 SEO：单页 14 语言的务实解法

### 3.1 现实约束（必须承认）

真正的 `hreflang` 要求**每种语言一个独立、可被单独抓取的 URL**。当前应用是**单文件、单 URL、靠 JS 字典切换**，不存在 `/en/`、`/zh/` 这类路径。因此：

- **不要伪造 `hreflang`** 指向 `?lang=en` 之类的查询参数——Google 对同一 URL 的参数 hreflang 支持很差，伪造反而可能被判为欺诈性标注。
- 搜索引擎/AI 爬虫不执行 JS，它们只看到一份静态 HTML。**这份静态 HTML 应该是英文**（主战场），而不是当前写死的 `zh-CN`。

### 3.2 约束内的最佳实践（按优先级）

**1. 静态 `<head>` 用英文 + canonical 唯一 URL**（已在 2.1 给出）

这是"机器视角"的版本：给搜索引擎和 AI 一个干净、一致、英文的入口。

**2. 真实用户切换语言时，用 JS 同步语言信号**（面向人，不影响爬虫）

在现有语言切换函数（设置 `I18N[code]` 的地方）追加：

```js
function applyLanguageSignals(code) {
  // 仅对真实用户生效；爬虫不会执行，故不影响静态英文 head
  document.documentElement.lang = code;                 // en / zh-CN / ja ...
  document.querySelector('meta[property="og:locale"]')
    ?.setAttribute('content', code.replace('-', '_'));  // en_US / zh_CN
  // 可选：按语言更新 title/description（利于用户分享 snippet）
  if (I18N_TITLES && I18N_TITLES[code]) document.title = I18N_TITLES[code];
}
// 在 loadLanguage / setLanguage 成功分支末尾调用：applyLanguageSignals(currentCode)
```

> 关键理解：这段 JS 改善的是**真实浏览器与分享卡片**的体验；静态英文 head 才是**抓取与引用**的依据。二者不冲突。

**3. 用 `og:locale:alternate` 声明存在其他语言版本**（已在 2.1 给出），这是单 URL 架构下对多语言最诚实的信号。

**4. x-default**：可在 `<head>` 追加 `<link rel="alternate" hreflang="x-default" href="https://fnhiq23.github.io/agi-engine-v3/">`，告诉引擎该 URL 是缺省版本。

**5. 中文内容的可抓取性**：把中文补充 FAQ 写成静态文本（同 2.3 手法，但用中文段落），放在同一页。爬虫能读到中文，未来即便做多语言也不需要改结构。

### 3.3 何时才升级为真正的多 URL（超出当前约束，仅记录）

若将来愿意从"单文件"扩展到"少量静态页"，可在仓库根目录新增 `index-en.html` / `index-zh.html` 两个静态入口页，各自写死独立 `<head>`，并用 `<link rel="alternate" hreflang="en|zh|x-default">` 互相指向。这是唯一能被 Google 正确识别的多语言方案；**在纯单文件约束下不建议做**。

### 做法 3｜权威目录 + 一致事实，让 AI 多源交叉验证

AI 会综合多个来源判断可信度。把同一个产品事实（名称、URL、一句话描述、价格、"自带 Key、无区块链"）在 **AlternativeTo、Product Hunt、G2/SaaSHub、GitHub README** 上保持一致。特别注意：

- **GitHub README 是最权威的机器可读源**。在 README 顶部加一段结构化的 "What is AGI Engine / Key facts / Pricing"，与 `llms.txt` 用词一致。
- 在 GitHub 仓库 Settings → 确保仓库描述与站点描述一致。
- 目录条目中的描述**逐字复用**同一句英文摘要，避免 AI 因措辞不一而降低置信度。
