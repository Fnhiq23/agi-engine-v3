# 分层开源战略与贡献者计划（AGI Engine）

> 本文件是执行方案，不是愿景文档。所有判断基于仓库当前真实状态：前端已托管在 GitHub Pages、`server/` 为 Node.js 后端、密钥只存在于被 gitignore 的环境文件中、收入 0 / 流量 0 / 日活 0。
> 硬边界：不虚假宣传、不提区块链或代币、不公开任何密钥或访问凭据、不承诺任何收入数字。

---

## 0. 决策一览（先给结论）

| 决策项 | 结论 | 一句话理由 |
|---|---|---|
| 是否开源 | 是，但**分层**开源 | 隐私产品的信任来自可审计；前端已公开且不可收回 |
| 开源范围 | 前端 + 脱敏后端参考实现 + 信任文档 + 模板 | 代码可审计，凭据/运营数据不出本地 |
| LICENSE | 前端 **MIT**（可附商标声明） | 最大化可审计与采用；白牌风险靠品牌与服务层对冲，而非靠许可证禁止转售 |
| 后端 | 代码选择性公开，密钥永不公开 | 公开支付验证逻辑能增强信任，但 `.env` / `.mail.env` / 数据库是红线 |
| DEL-001~006 | 选择性公开（脱敏后） | 增长/转化/定价属内部打法；其中信任文档单独完全公开 |
| 看板 | 看板源码可公开，线上数据与访问参数不公开 | 防止凭据外泄与真实数据被曲解 |

## 1. 第一性原理论证：为什么开源利大于弊

### 1.1 隐私产品的「可验证性」就是转化前置条件

隐私类产品卖的不是功能列表，而是**一个无法被证伪的承诺**。用户问的是："你说口令不落盘、不上传，凭什么信你？"

- 闭源回答：一份自我声明的隐私政策。
- 开源回答：用户或第三方可以打开 `index.html`，直接读 `SecureVault` 的实现，确认 AES-256-GCM、PBKDF2 迭代次数、口令不进入网络请求。

对注重隐私的付费人群（DEL-006 列出的 Target Persona），**代码可审计是把"我声称"变成"你可以验证"的唯一低成本手段**。没有可审计性，转化率 C 的上限被信任天花板锁死；而 DEL-000 已判定流量 T 是零因子，C 再优化也无法独自产生收入——但 C 是我们可以控制的变量，开源是提升 C 的杠杆。

### 1.2 前端已经公开，无法收回

- `index.html` 已部署在 GitHub Pages，仓库 `Fnhiq23/agi-engine-v3` 已存在。
- 这意味着前端代码在事实上已是公开资产。**不开源并不能让它变私密，只会让它显得"遮遮掩掩"**——这与隐私定位直接冲突。
- 与其被动接受"代码被人看到"，不如主动把它变成可信资产：加 LICENSE、加 README 验证指引、加 CONTRIBUTING，把"被人翻代码"转化为"被人审查并背书"。

### 1.3 护城河不在代码，在信任与流量

按 DEL-000 的收入拆解 `R = T × C × P`：

| 要素 | 开源的影响 | 是否构成护城河 |
|---|---|---|
| 客单价 P | 无直接影响；定价权来自定位与交付的价值 | 否 |
| 转化率 C | **正向**：可审计 → 隐私用户敢付 | 部分，但可复制 |
| 流量 T | **正向**：fork、翻译、开发者传播带来分发 | 是，但需持续运营 |
| 品牌信任 | **正向**：官方渠道 + 长期一致行为积累 | **是** |
| 代码实现 | 被任何人 fork | **否** |

结论：代码是**获客与信任的工具**，不是护城河。把代码锁起来不会保护收入，只会削弱信任和分发。真正的护城河是"官方渠道 + 持续兑现承诺 + 已建立的分发关系"，这些无法被 fork。

### 1.4 诚实的边界（开源做不到什么）

- 开源不会自动带来流量。T=0 时，R=0 的算术关系不因 LICENSE 改变。
- 开源不会自动带来收入。本项目不承诺任何金额。
- 开源允许他人合法 fork、修改甚至转售代码副本——这是许可证选择的代价，必须用品牌与服务层对冲（见 §3.4、§6）。

## 2. 分层清单：三类资产与逐项理由

### 2.1 判定标准

| 类别 | 判定标准 | 发布前动作 |
|---|---|---|
| 完全公开 | 不含任何凭据；公开后增强信任或可审计性；已无法收回 | 直接发布，附验证指引 |
| 选择性公开 | 不含密钥但含内部策略/架构/运营信息；脱敏后发布有净收益 | 人工脱敏 + 负责人复核 |
| 永不公开 | 含凭据、访问令牌、个人数据、生产数据库 | 保持 gitignore，禁止进聊天/日志/issue |

### 2.2 逐项归类（任务要求的七项）

| 资产 | 归类 | 理由 | 具体动作 |
|---|---|---|---|
| 前端 `index.html` | **完全公开** | 已在 GitHub Pages 公开、不可收回；包含全部加密实现，是信任审计的唯一入口；不含服务端密钥 | 保留公开；补 README「如何自行验证加密」章节，指向具体实现位置 |
| `server.js` | **选择性公开** | 代码本身从环境变量读取配置，不含硬编码密钥；公开支付 Webhook 验签逻辑能证明"伪造付款不激活"，是信任加分项。但公开前必须审查并参数化生产域名、sharecode 类访问参数、内部管理路径与任何硬编码 ID | 发布脱敏参考副本；生产部署配置、访问参数、管理端点细节留在私有仓库 |
| `server/.env` | **永不公开** | 含 PayPal Secret、`ADMIN_TOKEN`、Webhook ID、订阅计划 ID 等生产配置；泄露可导致伪造订阅、越权核销 | 保持 gitignore；轮换过任何曾出现在聊天记录中的凭据；模板只留占位符 |
| `server/.mail.env` | **永不公开** | 含 QQ 邮箱 SMTP 授权码，属于身份凭据；泄露可被用于冒充发信 | 保持 gitignore（权限 600）；示例文件只保留占位符 |
| DEL-001~006 策略文档 | **选择性公开** | 增长作战地图、转化漏斗、定价锚定、竞品分析属内部打法，全量公开等于给竞品送路线图；但脱敏后的"方法论/经验"是可传播内容 | 分为内部版与公开版：公开版删去渠道实验细节、内部 KPI 现状、具体投放参数；保留可复用的思路 |
| 信任文档（隐私政策、服务条款、退款政策、FAQ、付费墙信任文案） | **完全公开** | 这些文档本就是给最终用户看的承诺；与公开代码一致才能形成闭环。DEL-005 中标注「需创始人确认」的条款须先确认 | 占位符（邮箱、生效日期）填真实值后发布；凡标注待确认的条款确认前不对外生效 |
| 看板（`/dashboard` 及线上实例） | **选择性公开** | 看板 HTML 源码不含密钥，可作为"数据可验证"的证据；但线上实例带访问参数且显示真实的 0 收入/0 流量，公开参数等于泄露访问凭据 | 公开 `dashboard.html` 源码与**脱敏样例**报表结构；永不公开线上 URL、访问参数或原始 `db.json` |

### 2.3 公开前脱敏检查清单（每次发版前逐条打勾）

- [ ] `git grep -E 'SECRET|TOKEN|PASSWORD|授权码|sharecode'` 结果中无真实值
- [ ] `.env` / `.mail.env` / `server/data/*.json` 仍在 `.gitignore` 且未被 `git add -f` 强制提交
- [ ] 公开文档不含线上后端完整 URL 或访问参数
- [ ] 截图、录屏、示例数据中已抹去邮箱、客户端 ID、交易号
- [ ] DEL-005 中的占位符已替换、待确认条款已获确认
- [ ] `server.js` 脱敏副本中生产域名/计划 ID 已改为占位符

## 3. LICENSE 选择

### 3.1 三个方案对比

| 方案 | 对白牌转售的态度 | 对审计/采用的影响 | 法律确定性 | 适配度 |
|---|---|---|---|---|
| **MIT** | 明确允许出售与再分发代码副本 | 最宽松、最被广泛认可，审计友好 | 高，久经考验 | **推荐（前端）** |
| Apache-2.0 | 同样允许转售，但要求保留声明、附带专利授权 | 企业采用者更安心；条款更长 | 高 | 备选（若重视专利peace） |
| MIT + Commons Clause | 试图禁止"Sell 软件" | **不再被公认为开源**；"商业托管服务"是否算 Sell 存在解释空间，可能误伤自有 Pro 服务 | 较低，未经充分判例检验 | 仅在创始人明确要堵转售时采用 |

### 3.2 推荐决定

**主方案：MIT License + 独立商标声明。** 理由：

1. 隐私定位需要"最大可信度"，MIT 是开发者验证代码时最熟悉的信号。
2. 白牌风险的正确解法是**品牌与服务层**，不是限制代码使用权（详见 3.4）。
3. Commons Clause 的 "Sell" 定义可能覆盖我们自己的付费托管服务，给自己制造法律不确定性——**不把它作为默认方案**。

**备选**：若创始人坚持在许可证层面增加阻力，可在 MIT 后追加 Commons Clause 附录（见 3.3），但须同时接受"不再是 OSI 开源、部分开发者社区会因此拒绝贡献"的后果，并在 README 中如实说明。

### 3.4 防白牌的真实手段（不依赖许可证禁止转售）

| 手段 | 做法 | 为什么有效 |
|---|---|---|
| 商标声明 | `NOTICE` 中保留名称/标识权，要求衍生版本不得暗示官方身份 | 版权许可不能丢，但品牌不能白拿 |
| 官方渠道唯一化 | README 顶部列出且仅列出官方仓库与 Pages 域名 | 用户能识别冒牌，钓鱼站难以 claiming official |
| 服务层绑定 | 真实验签的订阅、持续更新、信任背书只在官方渠道提供 | fork 能复制代码，复制不了服务与信誉 |
| 可验证发布 | 为每个 release 生成 checksum 并公布验证方法 | 用户可确认下载的是未被篡改的官方版本 |

## 4. CONTRIBUTING 指南（可直接落地）

以下内容可直接作为 `CONTRIBUTING.md` 发布。

### 4.1 前置条件

- Node.js ≥ 18（后端与语法检查）、Python 3（启动静态服务器）、现代浏览器（需支持 Web Crypto）。
- 一个 GitHub 账号；不需要、也不应拥有本项目的生产凭据。
- 了解基本 Git 流程（fork → branch → commit → PR）。

### 4.2 本地运行

**只跑前端（推荐大多数贡献者）：**

```bash
git clone https://github.com/Fnhiq23/agi-engine-v3.git
cd agi-engine-v3
python3 -m http.server 8000
# 浏览器打开 http://localhost:8000
# 注意：Web Crypto 需要 HTTPS 或 localhost，直接双击 file:// 打开可能失效
```

前端是单文件，无需构建步骤。测试加密功能时请确认浏览器控制台无报错，并用"设置 → Privacy Vault"设置口令后加密/解密一条记忆做往返验证。

**跑后端（仅当需要改服务端逻辑时）：**

```bash
cd server
cp .env.example .env
# 编辑 .env：ADMIN_TOKEN 用 `openssl rand -hex 16` 生成；
# PayPal 一律使用 SANDBOX 测试凭据，不要填任何真实/生产值
node server.js
# 打开 http://localhost:3000/dashboard 查看本地样例数据
```

**硬性规则：**
- 永远不要提交 `.env`、`.mail.env`、`server/data/*.json`（它们已被 gitignore）。
- 永远不要把生产凭据、线上 URL、访问参数写进 issue、PR 描述、测试用例或截图。
- 需要真实支付联调时，只用 sandbox；生产环境的验证由维护者负责。

### 4.3 提交 PR 的流程

1. Fork 仓库，从 `main` 切出分支：`git checkout -b feat/简短描述`。
2. 做最小改动，一个 PR 只解决一个问题。
3. 自检：`node --check` 校验改动的 JS 代码块；前端用浏览器实测相关交互。
4. 提交信息采用 Conventional Commits：`feat: ...` / `fix: ...` / `docs: ...` / `i18n: ...`。
5. 推送并发 PR，描述中写明：改了什么、如何验证、是否涉及安全敏感代码。
6. 维护者 review；涉及加密/支付的改动需要额外的人工复核，可能要求补充测试用例。

### 4.4 最有价值的贡献方向

| 优先级 | 方向 | 为什么最有价值 | 交付形式 |
|---|---|---|---|
| P0 | 加密与安全审计 | 直接提升信任这一转化前提；口令处理、密文存储、导入导出边界是核心 | 审计报告、边界测试、修复 PR |
| P0 | Bug 复现与回归测试 | 项目真实经历过致命语法 Bug；可复现的测试能防止回归 | 最小复现步骤 + 测试脚本 |
| P1 | 现有 14 语言的翻译校对与新增语言 | 每一种语言对应一个可传播社群，直接贡献流量 T | `I18N` 字典 PR + 术语表 |
| P1 | 可访问性（a11y）与 PWA 离线体验 | 扩大可用人群，且改动局部、易审查 | 具体页面/组件 PR |
| P2 | 文档、验证教程、示例 | 降低"可审计"的使用门槛，让信任可被普通用户验证 | README/HOWTO 文档 PR |
| P2 | SEO/meta 与发布素材 | 延续 DEL-003 的可发现性工作 | 具体文案或 meta 代码 PR |
| — | 新功能大改 | 需先开 issue 讨论再动手，避免白做 | 先讨论，后 PR |

### 4.5 PR 描述模板

```
## 改了什么
（一两句话）

## 为什么改
（关联 issue 或说明问题）

## 如何验证
1.
2.

## 安全检查
- [ ] 没有引入任何密钥、令牌、真实凭据
- [ ] 没有改动加密/支付逻辑，或已附上额外说明
- [ ] 没有指向非官方渠道的链接
```

### 4.6 行为准则与安全披露

**行为准则（采用 Contributor Covenant 核心条款）：**

- 尊重不同背景、语言与观点的贡献者；禁止骚扰、人身攻击、歧视性言论。
- 禁止发布垃圾内容、广告、诱导安装或恶意代码。
- 维护者可编辑/拒绝不符合准则的内容，并保留封禁违规账号的权利。
- 违规举报渠道：通过仓库的私有联系渠道提交（在 README/仓库设置中配置，不公开个人邮箱以外的私人信息）。

**安全漏洞披露（重要）：**

- 发现漏洞请**私下**通过 GitHub Security Advisory 或仓库私有渠道报告，**不要**开公开 issue。
- 报告应包含：影响范围、复现步骤、建议修复；维护者确认并修复后再公开。
- 任何疑似已泄露的凭据，按"已暴露"处理并立即轮换，不在公开渠道讨论具体值。

## 5. 开源如何促进变现（三条真实机制）

> 以下均为机制描述，不含任何收入保证。开源只提高概率，不产生确定结果。

| 机制 | 因果链 | 落地动作 | 可验证信号 |
|---|---|---|---|
| ① 可审计 → 隐私用户敢付费 | 代码公开 → 第三方验证"口令不上传" → 信任提升 → 转化 C 提升 | README 增加"如何自行验证"章节，给出验证步骤与代码位置 | 用户 issue/讨论中提出具体审计问题；付费页引述公开实现 |
| ② 开发者二创 → 传播 → 流量 T | fork/翻译/集成 → 作者在博客/社区分享 → 曝光增加 → T 提升 | 欢迎翻译与工具集成 PR；维护 fork 友好文档；不阻碍合理二创 | 外部文章、Show HN/Reddit 提及、新增 star/fork 来源 |
| ③ 贡献者 → 推荐者/affiliate | 贡献者理解并背书 → 愿意推荐 → 带来有信任背书的新用户 | 建立推荐机制：利用现有 `/api/event` 的匿名 clientId 设计推荐链接与归因，制定透明的回报规则 | 推荐链接点击、归因事件、实际推荐行为 |

**对机制③的诚实说明**：affiliate 不是"发个承诺就自动发生"。它需要先实现推荐追踪与归因、明确回报与结算规则，且必须遵守平台规则。在那里之前，它只是方向，不是已上线功能。

## 6. 风险与对策（三条）

| 风险 | 具体表现 | 对策 | 责任动作 |
|---|---|---|---|
| ① 白牌与品牌冒充 | 他人 fork 后换名出售、冒充官方站点 | LICENSE + NOTICE 商标声明；README 只列官方渠道；release 公布 checksum 与验证方法；服务层（真实验签订阅、更新）只在官方渠道 | 每次发布附校验值；定期搜索冒充站点并向托管方举报 |
| ② 恶意使用与钓鱼 | 仿冒域名诱导用户输入 LLM API Key 或付款；在二创版本中植入窃取代码 | 产品文档明确"Key 永不发送到我们的后端"；官网显著展示官方渠道标识；提供"如何验证官方版本"指南；发现仿冒立即取证并投诉 | 建立仿冒举报入口；安全披露流程处理恶意 PR |
| ③ 凭据/数据泄露 | 贡献者误提交 `.env`；CI/日志泄露访问参数；生产数据外流 | 保持 gitignore；CI 加密钥扫描（如 gitleaks）；测试只用占位符与 sandbox；任何进过聊天/日志的凭据按已暴露处理并轮换；线上数据库永不提供公开访问 | 发版前执行 §2.3 清单；发现泄露先轮换再复盘 |

> 补充说明：公开 `server.js` 参考实现会暴露架构细节，但**验签逻辑公开本身是信任资产**；真正的攻击面在于凭据与部署配置，而非算法思路。因此分层策略的防御重心是"凭据不出本地"，而不是"代码不可读"。

## 7. 执行顺序（只排顺序，不承诺时间）

1. [ ] 创始人确认 LICENSE（MIT 主方案 / 可选 Commons Clause 附录）与 NOTICE 中的官方渠道表述。

8. [ ] 完成上述后，在仓库设置中启用安全披露渠道，再对外宣布开源。
